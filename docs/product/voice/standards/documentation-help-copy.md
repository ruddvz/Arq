# Documentation and help language

## Documentation mirrors the product contract

Docs do not get a looser truth standard than UI or marketing.

Every procedural instruction must be possible in the referenced build/release.

## Task-first headings

Prefer:

- Open a project read-only
- Recover local edits
- Export a plan sheet as PDF
- Resolve a sync conflict

Avoid:

- File management
- Miscellaneous
- Advanced workflow

when the user is trying to complete a specific task.

## State prerequisites

State prerequisites before steps:

> Requires Editor access and an open project.

Do not let the user reach step 6 before learning the action is unavailable to their role.

## Product names

Use exact canonical visible labels for menus, tabs, panels, modes, and tools.

Do not paraphrase:

> Open the properties sidebar.

when the actual visible name is:

> Open Inspector, then choose Properties.

## Versioning

If documentation applies only to a release/build, state it.

Do not write future docs in present tense.

## Screenshots

Screenshot captions and alt text must use the same canonical terms as the UI.

A UI rename is not complete until help images/captions are searched or marked stale.
