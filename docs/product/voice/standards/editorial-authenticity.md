# Editorial quality standard

This standard makes ARQ copy specific, inspectable and useful. It is not an
AI-authorship detector and must never be used to claim that a person or tool
wrote a passage.

The supplied reference is not a checklist of forbidden human traits. Title
case, curly punctuation, a single transition word, one word associated with a
model, or one punctuation mark cannot establish authorship and are not rejected
by this system for that reason. The system checks whether a pattern harms ARQ's
clarity, evidence or public trust boundary.

## The test

For public, support and documentation copy, review in this order:

1. Is the product fact true for the stated build and surface?
2. Does the sentence name the object, action, scope and relevant limit?
3. Does it tell the reader something new, or merely praise what was already said?
4. Can a reviewer trace the assertion to a source, test, state or decision?
5. Is the wording the shortest clear version for this surface?

If the answer to the first or fourth question is no, rewrite or remove the
claim. Style cannot repair unsupported product language.

## Prefer concrete evidence

Write the observed behaviour and the user consequence.

| Avoid                        | Write instead                                                                        |
| ---------------------------- | ------------------------------------------------------------------------------------ |
| A transformative way to work | Draw connected wall segments with snap and typed validation.                         |
| Built for confidence         | Show the blocking validation reason before the operation is applied.                 |
| A seamless file experience   | The selected file is compatible. Opening the project is not available in this build. |
| Experts agree                | Name the source and what it establishes, or omit the assertion.                      |
| ARQ represents a new era     | Remove it unless a concrete, supported claim follows.                                |

Do not add a second sentence that restates the first with a broader claim about
importance, the industry, the future or the reader's feelings.

## Structure

Use a heading when it helps a person find a task, capability, limit or decision.
Do not add a generic conclusion only to make a page feel finished. Do not force
a three-part list when two precise points are enough.

Transitions should state a relationship. `But`, `because`, `if` and `then` are
usually clearer than a decorative transition. Cut repeated connectors before
adding more explanation.

Do not use a formulaic negative contrast to create force. A sentence such as
"not every project" or "not a viewer but a workspace" needs a concrete
misunderstanding and a concrete correction. If it cannot supply both, state the
fact directly.

Do not call the product, its copy or its channels honest, real, genuine or
careful as a substitute for evidence. Let the source, constraint or observable
behaviour carry that weight.

## U+2014 in public and UI copy

Do not use U+2014 in public or product UI copy. Prefer a full stop, colon,
parentheses, semicolon or a shorter sentence. This is a hard house-style rule
because the deployed public site contains a concentrated pattern of clause
emphasis. It is not an AI-authorship signal and may not be described that way.

The source audit checks authored strings. The rendered-site audit checks HTML
after templates and entities are applied. The post-deploy verifier checks the
same rule on the response that visitors receive.

## Attribution

Do not invoke unnamed experts, users, observers, reports or critics. A source
must be named where it changes the reader's trust decision. If the source is not
appropriate for the surface, state the product fact without borrowed authority.

## Assistant-like filler

Do not begin a support answer with agreement, a promise of help or a generic
disclaimer. Start with the current state or the next action. Offer a follow-up
only when the user has a real choice or the system needs a specific detail.

## Review-required patterns

The audit flags review-required patterns such as unsupported significance,
vague attribution, canned reassurance, promotional ornament and stock
conclusions. A finding is a prompt to inspect meaning, not proof of an issue.

An acknowledgement is temporary. It must name the evidence, reviewer role,
reason and expiry. It cannot suppress a hard claim, an active conflict or a
missing public-copy inventory entry.

Hard rules cannot be acknowledged. In particular, an acknowledgement cannot
permit U+2014 in public or UI copy.

## Surface differences

- Product UI: use literal labels and state transitions. Do not optimise for
  variety at the expense of recognition.
- Support: lead with the answer, then provide the smallest safe diagnostic path.
- Documentation: explain mechanism only when it helps a reader act or evaluate a
  limit.
- Marketing: use a memorable headline only when its body copy can prove the
  narrow claim it implies.
- Localisation: preserve meaning, variables, severity and action. A translator
  may replace an English idiom rather than preserve it.
