# UX, language, brand, and public claims

## Authority boundary

The repository's ARQ Language System owns canonical wording, state labels, public claims, conflict records, and rendered-site checks. Canonical brand assets and tokens own the logo and visual identity. This Project may critique and propose changes, but repository sources decide accepted wording and assets.

## Current source conflict

This Project uses `ARQ` publicly, while the observed repository and deployed site render `Arq`. Treat casing as a governed conflict, not a stylistic preference. Do not bulk-replace either form until the Language System and brand owner record the resolution and update validators, assets, metadata, and public copy together.

## Professional instrument UX

ARQ should make these distinctions visible:

- selected file versus opened working project;
- compatible file versus complete current data;
- browser journal versus portable `.arq` save;
- local save versus sync;
- current revision versus stale proposal;
- preview versus committed operation;
- imported source versus native semantic result;
- derived view versus canonical model;
- verified result versus unsupported or blocked action;
- recoverable action versus permanent deletion.

## Operator UX for this Project

Every substantial response should expose:

- source authority and snapshot date;
- requested delivery stop;
- exact write actions, if any;
- status labels: Completed, Verified, Inferred, Assumed, Blocked, Failed;
- conflicts and stale sources;
- checks and actual results;
- remaining proof gaps;
- next concrete action.

Do not bury a failed check below a confident summary. Do not present tool capability as work completed.

## Error design

Errors should state:

1. what failed;
2. why it failed, when known;
3. what was affected;
4. what remains safe;
5. whether the user can retry, repair, open read-only, recover, or roll back;
6. the evidence or diagnostic reference.

Avoid generic `Something went wrong`, false success, or a retry that repeats the same unexamined state.

## Public claim gate

Do not publish current-tense claims for:

- shipped or generally available status;
- full project open and portable save;
- sync, collaboration, or multi-user guarantees;
- native app availability;
- broad platform support;
- full IFC, DXF, PDF, or other interchange fidelity;
- AI authoring in the product;
- security certifications, compliance, or data residency;
- recovery, uptime, performance, accuracy, or productivity guarantees;
- pricing, launch dates, user counts, adoption, or savings;
- professional, code, structural, or safety approval;

unless a current Language System binding and scoped implementation or release evidence support the exact wording.

## UI/UX source improvements

- Link every spec surface to a capability state and implementation path.
- Add empty, loading, offline, stale, conflict, permission, cancellation, failure, and recovery states to every interactive flow.
- Keep touch, keyboard, screen reader, reduced motion, long content, localisation, and high-DPI evidence in acceptance.
- Separate visual reference fidelity from behaviour and product truth.
- Require before-and-after screenshots only for surfaces actually changed and visually observed.
- Add a state-language adapter so persistence and AI states come from canonical machine state rather than ad hoc copy.
